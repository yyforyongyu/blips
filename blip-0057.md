## Abstract

This bLIP defines an optional BOLT 12 offer TLV that advertises an
HTTPS endpoint for exchanging BOLT 12 `invoice_request` and `invoice`
messages.

A payer that supports this bLIP can send an encoded BOLT 12
`invoice_request` to the endpoint via HTTPS `POST` and receive an
encoded BOLT 12 `invoice` in the HTTPS response.

This bLIP only specifies an alternate transport for the interactive
BOLT 12 invoice request flow. It does not change BOLT 12 offer,
invoice request, invoice, or payment semantics.

## Motivation

BOLT 12 offers are transport-independent objects, but the standard
interactive flow exchanges `invoice_request` and `invoice` messages over
onion messages. Some deployments already have HTTPS infrastructure and
may want to support BOLT 12 offers before they can reliably receive
onion messages.

This bLIP provides a minimal HTTPS transport that preserves BOLT 12
object semantics. Payers still construct standard `invoice_request`
objects and must still validate returned `invoice` objects according to
BOLT 12.

This is a direct sender-to-receiver bridge for the BOLT 12 invoice-fetch
step. It brings the deployment simplicity of direct BOLT 11 or LNURL-pay
style delivery to BOLT 12 objects, while keeping BOLT 12's reusable offers
and signed invoice validation.

## Specification

### Offer TLV

This bLIP defines the following BOLT 12 offer TLV:

1. `tlv_stream`: `offer`
2. types:
    1. type: 1000000059 (`offer_invoice_request_https_endpoint`)
    2. data:
        * [`...*utf8`:`url`]

The `url` field contains the HTTPS endpoint to which a payer can send an
encoded BOLT 12 `invoice_request`.

### Offer Requirements

The writer of an offer:

* MAY include `offer_invoice_request_https_endpoint` to advertise support
  for this bLIP.
* If it includes `offer_invoice_request_https_endpoint`:
  * MUST include `offer_issuer_id`.
  * MUST include a valid `offer_signature` as defined in [bLIP 56][].
  * MUST set `url` to a valid absolute URI with a non-empty authority and
    host.
  * MUST use the `https` URI scheme.
  * MUST NOT include a URI fragment.
  * MUST NOT include URI userinfo.
  * MUST ensure the UTF-8 encoding of `url` is at most 1024 bytes.
  * SHOULD use a canonical URL form, including lowercase scheme and host,
    no explicit default port, and no superfluous trailing slash.
  * SHOULD use an endpoint that remains usable until the offer expires.

The reader of an offer:

* MAY ignore `offer_invoice_request_https_endpoint`.
* MUST ignore `offer_invoice_request_https_endpoint` if the `url` is not
  a valid absolute URI with a non-empty authority and host.
* MUST ignore `offer_invoice_request_https_endpoint` if the URI scheme is
  not `https`.
* MUST ignore `offer_invoice_request_https_endpoint` if the URI contains a
  fragment.
* MUST ignore `offer_invoice_request_https_endpoint` if the URI contains
  userinfo.
* MUST ignore `offer_invoice_request_https_endpoint` if the UTF-8 encoding
  of `url` is more than 1024 bytes.
* MUST ignore `offer_invoice_request_https_endpoint` if the offer does not
  contain `offer_issuer_id`.
* MUST ignore `offer_invoice_request_https_endpoint` if the offer does not
  contain a valid `offer_signature` as defined in [bLIP 56][].

If an offer contains both `offer_paths` and
`offer_invoice_request_https_endpoint`, the payer MAY use either the
standard onion-message transport or the HTTPS transport defined in this
bLIP.

When using the HTTPS transport, the payer MUST use `offer_issuer_id` as
the expected BOLT 12 `invoice_node_id` for the returned invoice, even if
the offer also contains `offer_paths`.

### Invoice Request

The payer constructs a BOLT 12 `invoice_request` exactly as specified by
BOLT 12.

The payer sends the encoded invoice request to the HTTPS endpoint with:

* HTTP method: `POST`.
* `Content-Type`: `text/plain; charset=us-ascii`.
* Request body: the encoded BOLT 12 invoice request string, beginning
  with `lnr`.

The request body:

* MUST contain exactly one encoded BOLT 12 invoice request.
* MUST use the BOLT 12 invoice request human-readable prefix `lnr`,
  case-insensitively.
* MUST NOT exceed 65536 bytes.
* MUST NOT contain leading or trailing whitespace.
* SHOULD use lowercase encoding.
* SHOULD NOT contain `+` continuation markers or embedded whitespace.

The payer:

* MUST NOT connect to an endpoint address that is loopback, link-local,
  private, or otherwise special-use unless explicitly configured to allow
  it.
* MUST apply the preceding address check to the concrete IP address used
  for every connection attempt, retry, and reconnect, and MUST NOT allow
  the HTTP stack to re-resolve the endpoint host to an unchecked address.
* MUST fail the HTTPS transport attempt if no endpoint address remains that
  it is allowed to connect to.
* MUST NOT send cookies, HTTP authentication credentials, or bearer
  tokens unless explicitly configured to do so by the user or
  application.
* SHOULD NOT send a `Referer` header.
* SHOULD use a generic `User-Agent` header that does not identify the
  wallet implementation, version, build, device, or user.
* MUST NOT follow HTTP redirects.

### Invoice Response

On success, the endpoint responds with:

* HTTP status: `200 OK`.
* `Content-Type`: `text/plain; charset=us-ascii`.
* Response body: the encoded BOLT 12 invoice string, beginning with
  `lni`.

The response body:

* MUST contain exactly one encoded BOLT 12 invoice.
* MUST use the BOLT 12 invoice human-readable prefix `lni`,
  case-insensitively.
* MUST NOT contain leading or trailing whitespace.
* MUST NOT exceed 65536 bytes.

The payer:

* MUST abort if the `Content-Length` header indicates a response body
  exceeding 65536 bytes.
* MUST abort if the response body exceeds 65536 bytes while being read.
* MUST parse the response body as a BOLT 12 `invoice`.
* MUST validate the invoice according to BOLT 12.
* MUST reject the invoice if any field in the ranges copied from the
  `invoice_request` is missing from the invoice or does not exactly match
  the invoice request.
* MUST reject the invoice if `invoice_node_id` is not equal to the
  `offer_issuer_id` from the offer.
* MUST reject the invoice if its signature is not valid for
  `invoice_node_id`.
* MUST NOT treat HTTPS certificate validation as a substitute for BOLT 12
  invoice signature validation.

The BOLT 12 requirements that an invoice response arrive via the
`onionmsg_tlv` `reply_path`, or via an `invreq_paths` blinded path if the
`invoice_request` contains `invreq_paths`, do not apply when the payer
intentionally uses the HTTPS transport defined in this bLIP.

### Error Responses

If the endpoint cannot return an invoice, it SHOULD respond with a
non-`200` HTTP status code and `Content-Type: application/json`.

The response body SHOULD be a JSON object with the following fields:

```json
{
  "code": "invalid_invoice_request",
  "message": "The invoice request could not be parsed."
}
```

`code` is a short ASCII string intended for machine handling. `message`
is a human-readable string intended for diagnostics.

The following error codes are defined:

| HTTP Status | Code                      | Description                                              |
|-------------|---------------------------|----------------------------------------------------------|
| 400         | `invalid_invoice_request` | The request body is not a valid BOLT 12 invoice request. |
| 404         | `unknown_offer`           | The invoice request does not match a known offer.        |
| 410         | `offer_expired`           | The matching offer has expired.                          |
| 422         | `rejected`                | The invoice request is valid but was rejected.           |
| 429         | `rate_limited`            | The endpoint is rate-limiting this client or request.    |
| 503         | `temporarily_unavailable` | The endpoint cannot currently generate an invoice.       |

The endpoint SHOULD include a standard HTTP `Retry-After` header in `429`
and `503` responses indicating when the payer may retry.

The payer:

* MUST treat any non-`200` response as failure to obtain an invoice.
* MUST abort if the `Content-Length` header indicates an error response
  body exceeding 65536 bytes.
* MUST abort if the error response body exceeds 65536 bytes while being
  read.
* MUST ignore the error response body unless it parses as a UTF-8 JSON
  object without duplicate `code` or `message` member names, containing a
  string `code` field whose value is one of the error codes defined in
  this section, and containing a string `message` field.
* SHOULD NOT directly display the `message` field to users unless it has
  filtered problematic characters.
* SHOULD respect a standard HTTP `Retry-After` header when present in a
  `429` or `503` response.
* MAY retry transient errors according to local policy, and SHOULD use
  exponential backoff when retrying without a `Retry-After` header.

### Endpoint Behavior

The endpoint receiving an HTTPS invoice request:

* MUST reject the request if the `Content-Length` header indicates a
  request body exceeding 65536 bytes.
* MUST abort if the request body exceeds 65536 bytes while being read.
* MUST parse the request body as exactly one encoded BOLT 12
  `invoice_request`.
* MUST validate the invoice request according to BOLT 12, except that the
  request is allowed to arrive over the HTTPS transport defined in this
  bLIP instead of over onion messages.
* MUST NOT reject or ignore the invoice request solely because the
  matching offer contains `offer_paths` and the invoice request did not
  arrive via one of those blinded paths.
* MUST NOT reject or ignore the invoice request solely because it contains
  `invreq_paths` that cannot be used for the HTTPS response.
* MUST verify that the invoice request matches a valid offer whose
  `offer_invoice_request_https_endpoint` `url` exactly matches the
  advertised endpoint URL that received the request.
  If multiple advertised endpoint URLs route to the same handler, the
  handler MUST know which advertised URL was used and apply this check to
  that URL.
* MUST set `invoice_node_id` in the returned invoice to `offer_issuer_id`.
* MUST sign the invoice according to BOLT 12.
* MAY return the same invoice for a repeated invoice request with the same
  `invreq_metadata`, as allowed by BOLT 12.
* SHOULD deduplicate concurrent requests with identical `invreq_metadata`
  and return the same invoice for each.

The endpoint SHOULD impose reasonable rate and resource limits, and
MUST NOT return response bodies exceeding 65536 bytes.

## Rationale

The TLV value is a UTF-8 string because BOLT 12 already uses `...*utf8`
for human-readable strings, and URIs are naturally represented as text.
The URI is nevertheless restricted to `https` because the invoice request
may contain payer-specific data and should not be exposed to passive
network observers.
The offer TLV type is an arbitrary unused odd type in the BOLT 12
offer-extension range. It is odd because this transport is optional and
readers that do not understand it can ignore it; it is not intended to
encode the bLIP number and should not change solely because this bLIP is
renumbered.

The request and successful response use `text/plain` bodies containing
the BOLT 12 encoded objects directly. This avoids defining a second object
encoding and makes the HTTPS transport a thin wrapper around existing BOLT
12 objects.
The `us-ascii` charset is used because BOLT 12 bech32 encodings are ASCII.
The 65536-byte body limit is intended to bound resource use while remaining
well above typical BOLT 12 request and invoice sizes.
If an offer advertises multiple alternate transports, the issuer SHOULD
ensure returned invoice encodings fit within the lowest limit among the
advertised transports it expects payers to use.

Errors use HTTP status codes and JSON bodies because BOLT 12
`invoice_error` does not currently define a widely-used standalone text
encoding analogous to `lnr` or `lni`.

Related work includes [LNURL-pay][], [BIP-353][], [bLIP 56][], and
HTTP-to-BOLT12 proxy services. LNURL-pay and Lightning Address use HTTPS
to obtain BOLT 11 invoices, but they do not carry BOLT 12
`invoice_request` and `invoice` objects or provide BOLT 12 invoice
signature binding to `offer_issuer_id`. BIP 353 discovers BOLT 12 offers
via DNS payment instructions, but does not transport the interactive
invoice request flow. An offer carrying this TLV MAY be distributed via
BIP 353, which composes DNS offer discovery with HTTPS invoice-request
transport. bLIP 56 signs the offer so that the HTTPS endpoint is bound to
`offer_issuer_id` before the payer sends an `invoice_request`. Services
such as [bootstrap.bolt12.org][] and the [Boltz BOLT12 API][] expose HTTP
APIs that proxy to BOLT 12 onion messages server-side; this bLIP instead
lets the offer issuer advertise its own HTTPS endpoint and use HTTPS as
the end-to-end transport for this flow.

The manual exchange in [bLIP 58][] defines a local, user-mediated
alternative for QR, copy-paste, NFC, or file handoff. This bLIP instead
defines an automated HTTPS endpoint advertised in the offer.

The offer is required to include `offer_issuer_id` because HTTPS does not
provide the onion-message path context used by BOLT 12 offers containing
only `offer_paths`. The payer can instead verify that the returned invoice
is signed by the advertised `offer_issuer_id`.

When this transport is intentionally used, BOLT 12 onion-message arrival
checks for `offer_paths`, `reply_path`, and `invreq_paths` are replaced by
HTTPS delivery and BOLT 12 invoice signature validation. All BOLT 12 object
validation that does not depend on onion-message delivery still applies.

## Privacy and Security Considerations

HTTPS transport has weaker privacy properties than onion messages.

Using this bLIP can reveal the following information to the endpoint, its
hosting provider, reverse proxy, CDN, DNS resolver, TLS infrastructure, or
network observers:

* The payer's IP address or proxy address.
* DNS lookup metadata.
* TLS SNI and TLS fingerprinting metadata.
* HTTP headers such as `User-Agent`.
* Request timing and retry patterns.
* The specific endpoint URL used by the offer.
* Correlation between repeated requests to the same endpoint.

The endpoint operator can also observe the full `invoice_request`, which
may include amount, quantity, payer note, and payer public key fields.
This is expected because the endpoint is the offer issuer, but the HTTPS
transport can make this metadata easier to correlate with network-layer
metadata.
If the offer was discovered via BIP 353, DNS discovery metadata is
additional to the HTTPS transport metadata described here and is visible to
different observers.

The signed-offer requirement in this bLIP prevents endpoint-substitution
relay attacks before the payer sends an `invoice_request`: a party that
changes only the HTTPS endpoint in an otherwise real signed offer cannot
produce a valid `offer_signature`. The endpoint-binding requirements at the
issuer provide an additional check that the invoice request matches the
advertised endpoint used by the offer. This does not authenticate the offer
identity by itself. If an attacker substitutes an entirely different signed
offer, the returned invoice can still validate under the attacker's
`offer_issuer_id`; preventing that requires authenticated offer delivery or
an independently known issuer key.

Payers SHOULD prefer standard BOLT 12 onion-message transport when it is
available and reliable. Wallets SHOULD make the privacy tradeoff clear to
users when HTTPS transport is used interactively.

Payers SHOULD use fresh `invreq_metadata` and a fresh `invreq_payer_id` for
each invoice request, as required by BOLT 12, and MUST NOT reuse payer keys
across requests in a way that creates additional correlation.

The mandatory endpoint address checks in this bLIP reduce SSRF and local
network probing risks, especially for wallets and services running in
privileged or server-side environments.

## Universality

This feature is optional and is not intended to be universal. BOLT 12 onion
messages remain the standard transport for interactive BOLT 12 invoice
requests.

This bLIP is intended for deployments that need an HTTPS fallback or
out-of-band transport while preserving BOLT 12 object semantics.

## Backwards Compatibility

Older BOLT 12 readers that do not understand
`offer_invoice_request_https_endpoint` can ignore it and use standard BOLT
12 onion-message transport if the offer contains usable routing
information.

Offers that rely exclusively on this bLIP will not be payable by wallets
that do not implement this bLIP.
