## Abstract

This bLIP defines an optional BOLT 12 offer TLV that advertises a Nostr
endpoint for exchanging BOLT 12 `invoice_request` and `invoice` messages.

A payer that supports this bLIP can send an encoded BOLT 12
`invoice_request` to the offer issuer using [NIP-59][] gift-wrapped
Nostr messages and receive an encoded BOLT 12 `invoice` in a Nostr
response message.

This bLIP only specifies an alternate transport for the interactive BOLT
12 invoice request flow. It does not change BOLT 12 offer, invoice
request, invoice, or payment semantics.

## Motivation

Some [BOLT 12][] deployments may want an asynchronous relay-based transport
for exchanging invoice requests and invoices. Nostr provides a widely
deployed relay network and encrypted private messaging conventions that
can be used as a side-channel while preserving BOLT 12 object semantics.

This bLIP keeps the Nostr transport separate from the HTTPS transport in
[bLIP 57](./blip-0057.md), because Nostr has different delivery,
encryption, relay, retry, and privacy properties.

Unlike the direct HTTPS and manual transports, this bLIP uses
relay-mediated delivery. It is intended for Nostr-native or
async-tolerant contexts that want to preserve BOLT 12 object semantics
without requiring the offer issuer to operate an HTTPS endpoint.

## Specification

### Offer TLV

This bLIP defines the following BOLT 12 offer TLV:

1. `tlv_stream`: `offer`
2. types:
    1. type: 1000000061 (`offer_invoice_request_nostr_endpoint`)
    2. data:
        * [`32*byte`:`recipient_pubkey`]
        * [`u8`:`relay_count`]
        * [`relay_count*nostr_relay`:`relays`]

1. subtype: `nostr_relay`
2. data:
    * [`u8`:`url_len`]
    * [`url_len*byte`:`url`]

`recipient_pubkey` is the 32-byte x-only Nostr public key to which invoice
request messages should be addressed.
A valid x-only Nostr public key is 32 bytes that decode to the x-coordinate
of a valid point on secp256k1, as specified by [BIP-340][] and [NIP-01][].

`relays` is the list of Nostr relay URLs to which invoice request messages
should be published.
Each `url` is the UTF-8 encoding of a Nostr relay URL. `url_len` is the
byte length of `url`.

### Offer Requirements

The writer of an offer:

* MAY include `offer_invoice_request_nostr_endpoint` to advertise support
  for this bLIP.
* If it includes `offer_invoice_request_nostr_endpoint`:
  * MUST include `offer_issuer_id`.
  * MUST include a valid `offer_signature` as defined in [bLIP 56][].
  * MUST set `recipient_pubkey` to a valid x-only Nostr public key.
  * MUST control the private key corresponding to `recipient_pubkey`.
  * MUST NOT advertise another simultaneously valid offer with
    `offer_invoice_request_nostr_endpoint` using the same
    `recipient_pubkey`.
  * MUST set `relay_count` to at least 1 and at most 5.
  * MUST ensure every relay URL is a valid absolute URI with a non-empty
    authority and host.
  * MUST ensure every relay URL uses the `wss` URI scheme.
  * MUST NOT include URI fragments or userinfo in relay URLs.
  * MUST ensure every relay URL is at least 1 byte and at most 255 bytes
    when UTF-8 encoded.
  * SHOULD use a Nostr key and relay set that remain usable until the
    offer expires.

The reader of an offer:

* MAY ignore `offer_invoice_request_nostr_endpoint`.
* MUST ignore `offer_invoice_request_nostr_endpoint` if the offer does not
  contain `offer_issuer_id`.
* MUST ignore `offer_invoice_request_nostr_endpoint` if the offer does not
  contain a valid `offer_signature` as defined in [bLIP 56][].
* MUST ignore `offer_invoice_request_nostr_endpoint` if `recipient_pubkey`
  is not a valid x-only Nostr public key.
* MUST ignore any relay URL that is not a valid absolute URI with a
  non-empty authority and host using the `wss` scheme.
* MUST ignore any relay URL that contains a URI fragment or userinfo.
* MUST ignore `offer_invoice_request_nostr_endpoint` if `relay_count` is
  0 or greater than 5.
* MUST ignore `offer_invoice_request_nostr_endpoint` if its encoded data
  does not parse to exactly `relay_count` `nostr_relay` records.
* MUST NOT use this transport if no valid relay URL remains.

If an offer contains both `offer_paths` and
`offer_invoice_request_nostr_endpoint`, the payer MAY use either the
standard onion-message transport or the Nostr transport defined in this
bLIP.

When using the Nostr transport, the payer MUST use `offer_issuer_id` as
the expected BOLT 12 `invoice_node_id` for the returned invoice, even if
the offer also contains `offer_paths`.

### Nostr Message Format

Messages for this bLIP MUST use [NIP-59][] gift wraps with [NIP-44][]
encryption.

This bLIP follows the private-message envelope pattern used by [NIP-17][],
but intentionally defines its own rumor event kind instead of using the
NIP-17 `kind 14` chat message.

[NIP-04][] encrypted direct messages MUST NOT be used.

This bLIP defines the following Nostr rumor event kind:

* `21059`: BOLT 12 invoice request transport message.

The rumor event content contains the transport payload. The rumor event is
sealed and gift-wrapped according to [NIP-59][] before being published to
relays.

Implementations MUST ignore a message whose outer gift-wrap event is not a
[NIP-59][] `kind:1059` gift wrap. Implementations MUST validate the signed
gift-wrap event id, pubkey, and signature as specified by [NIP-01][]
before decrypting the gift-wrap content to obtain the seal event.
Implementations MUST ignore a message whose decrypted seal event is not a
[NIP-59][] `kind:13` seal event or whose seal event contains any tags.
Implementations MUST validate the signed seal event id, pubkey, and
signature as specified by [NIP-01][] before decrypting the seal content to
obtain the rumor event.
Rumor events are unsigned as specified by [NIP-59][]; implementations MUST
ignore a message whose decrypted rumor is not an unsigned rumor event,
MUST compute and validate rumor event ids, and MUST NOT require rumor
event signatures.
After decrypting the rumor event and before inspecting its tags or content,
implementations MUST verify that the signed seal event pubkey matches the
decrypted rumor event pubkey, as specified by [NIP-17][]. Messages failing
this sender-binding check MUST be ignored.
Implementations MUST follow [NIP-59][] requirements for gift-wrap signing
keys and timestamps, including using random one-time-use gift-wrap signing
keys and randomized `created_at` values.
Implementations MUST NOT create a gift wrap unless both the serialized
rumor event and the serialized seal event fit within the [NIP-44][]
plaintext size limit before being encrypted by their respective layers.
The serialized seal event size check MUST be performed after the encrypted
rumor ciphertext has been placed in the seal event content.
Implementations MUST NOT create a gift wrap whose outer `kind:1059` event
JSON exceeds 131072 bytes when UTF-8 encoded. Receivers MUST ignore any
received outer `kind:1059` event whose event JSON exceeds 131072 bytes
when UTF-8 encoded before validating its event id or signature.

The following encrypted rumor tags are defined:

| Tag                         | Description                                  |
|-----------------------------|----------------------------------------------|
| `["bolt12", "request"]`   | The content is an encoded `lnr...` request.  |
| `["bolt12", "invoice"]`   | The content is an encoded `lni...` invoice.  |
| `["bolt12", "error"]`     | The content is a JSON error object.          |
| `["e", request_rumor_id]`  | A response to the request with this rumor id.|
| `["relay", relay_url]`     | A relay where the sender will await replies. |

These tags are inside the encrypted rumor and are not relay-indexed.
Nostr public keys and event ids in these tags MUST be encoded as
lowercase 64-character hexadecimal strings, as specified by [NIP-01][].
Readers MUST ignore any rumor whose `p` or `e` tag values inspected by
this bLIP are not lowercase 64-character hexadecimal strings.
Tag requirements in this bLIP match the tag name and the listed element
values. Additional tag elements are allowed and ignored by this bLIP unless
explicitly prohibited. For example, `["p", pubkey]` means a tag whose
first element is `p` and second element is `pubkey`; it does not prohibit
additional elements allowed by [NIP-01][]. Exact-one requirements count
tags by these matched elements unless a rule explicitly counts all tags
with the same tag name.
Outer gift-wrap public `p` recipient checks count all public `p` tags in
the gift wrap: the gift wrap MUST contain exactly one public `p` tag, and
that tag's second element MUST be the expected recipient pubkey.
Encrypted rumor `p` recipient checks count all `p` tags in the rumor: the
rumor MUST contain exactly one `p` tag, and that tag's second element MUST
be the expected recipient pubkey.
The `bolt12` tag is defined by this bLIP, and its second element is the
message discriminator.
Every rumor event for this bLIP MUST contain exactly one `bolt12` tag,
whose second element is exactly one of `request`, `invoice`, or `error`.
The three discriminator values are mutually exclusive. Readers MUST ignore
rumor events that contain zero `bolt12` tags, more than one `bolt12` tag,
or an unknown discriminator.
Every `invoice` or `error` response rumor MUST contain exactly one `e` tag
total, and that tag's second element MUST be the request rumor id. Readers
MUST ignore response rumors that contain zero `e` tags, more than one `e`
tag, or a sole `e` tag that does not reference the expected request rumor
id.

### Invoice Request

The payer constructs a BOLT 12 `invoice_request` exactly as specified by
BOLT 12.

The payer:

* MUST generate a fresh Nostr key pair for each invoice request.
  The public key of this fresh key pair is called `payer_pubkey`.
* MUST set the request rumor event `pubkey` field to `payer_pubkey` and
  MUST use the corresponding private key to sign the request seal event.
* MUST create a Nostr rumor event with kind `21059`.
* MUST set the rumor `content` to exactly one encoded BOLT 12 invoice
  request string, beginning with `lnr`.
* MUST use the BOLT 12 invoice request human-readable prefix `lnr`,
  case-insensitively.
* MUST ensure the rumor `content` is at most 32768 bytes when UTF-8
  encoded.
* MUST include exactly one `["bolt12", "request"]` tag.
* MUST include exactly one `p` tag, and MUST set that tag's second element
  to `recipient_pubkey`, encoded as a lowercase 64-character hexadecimal
  string.
* SHOULD include one or more `["relay", relay_url]` tags indicating
  relays where it will await a response.
* MUST NOT include more than 5 `["relay", relay_url]` tags.
* MUST ensure every `["relay", relay_url]` tag uses a valid absolute URI
  with a non-empty authority and host, the `wss` scheme, no URI fragment,
  no URI userinfo, and a UTF-8 encoding of at least 1 byte and at most 255
  bytes.
* MUST seal and gift-wrap the rumor according to [NIP-59][] addressed to
  `recipient_pubkey`.
* MUST include exactly one public `p` tag in the outer `kind:1059` gift
  wrap, and that tag's second element MUST be `recipient_pubkey`.
* MUST NOT connect to any relay address from the offer that is loopback,
  link-local, private, or otherwise special-use unless explicitly
  configured to allow it.
* MUST apply the preceding address check to the concrete IP address used
  for every relay connection attempt, retry, and reconnect, and MUST NOT
  allow the WebSocket stack to re-resolve a relay host to an unchecked
  address.
* MUST fail the Nostr transport attempt if no offer relay remains that it
  is allowed to connect to.
  The payer MAY then fall back to another transport advertised in the
  offer.
* MUST publish the resulting [NIP-59][] gift wrap to one or more relays
  from the offer that it is allowed to connect to.

The invoice request content:

* MUST contain exactly one encoded BOLT 12 invoice request.
* MUST use the BOLT 12 invoice request human-readable prefix `lnr`,
  case-insensitively.
* MUST NOT exceed 32768 bytes when UTF-8 encoded.
* MUST NOT contain leading or trailing whitespace.
* SHOULD use lowercase encoding.
* SHOULD NOT contain `+` continuation markers or embedded whitespace.

The payer MUST subscribe for responses on every relay advertised in the
offer to which it published the request, and on every relay it advertised
with a `["relay", relay_url]` tag.

### Invoice Response

The offer issuer receiving a Nostr invoice request:

* MUST, before decrypting the gift-wrap content, validate the outer
  gift-wrap event kind, id, pubkey, and signature as specified above.
* MUST, before decrypting the gift-wrap content, ignore the message if the
  outer `kind:1059` gift wrap does not contain exactly one public `p` tag,
  or if that tag's second element is not the `recipient_pubkey` of exactly
  one of the issuer's advertised offers that includes
  `offer_invoice_request_nostr_endpoint`.
  This is the selected offer referenced by the following checks.
* MUST unwrap the [NIP-59][] message.
* MUST ignore the message if the decrypted rumor event kind is not
  `21059`.
* MUST ignore the message if it does not contain exactly one
  `["bolt12", "request"]` tag.
* MUST ignore the message if it does not contain exactly one `p` tag, or
  if that tag's second element does not match the `recipient_pubkey` from
  the selected offer.
* MUST ignore all `["relay", relay_url]` tags after the first 5.
* MUST ignore any `["relay", relay_url]` tag whose `relay_url` is not a
  valid absolute URI with a non-empty authority and host using the `wss`
  scheme, or whose URI contains a fragment or userinfo, or whose UTF-8
  encoding is less than 1 byte or more than 255 bytes.
* MUST NOT connect to relay addresses that are loopback, link-local,
  private, or otherwise special-use unless explicitly configured to allow
  them.
* MUST apply the preceding address check to the concrete IP address used
  for every relay connection attempt, retry, and reconnect, and MUST NOT
  allow the WebSocket stack to re-resolve a relay host to an unchecked
  address.
* MUST ignore the message if the rumor content exceeds 32768 bytes when
  UTF-8 encoded.
* MUST parse the rumor content as exactly one encoded BOLT 12
  `invoice_request`.
* MUST validate the invoice request according to BOLT 12, except that the
  request is allowed to arrive over the Nostr transport defined in this
  bLIP instead of over onion messages.
* MUST NOT reject or ignore the invoice request solely because the
  matching offer contains `offer_paths` and the invoice request did not
  arrive via one of those blinded paths.
* MUST NOT reject or ignore the invoice request solely because it contains
  `invreq_paths` that cannot be used for the Nostr response.
* MUST verify that the invoice request matches the selected offer.
* MUST set `invoice_node_id` in the returned invoice to `offer_issuer_id`
  from the selected offer.
* MUST sign the invoice according to BOLT 12.

On success, the offer issuer:

* MUST create a Nostr rumor event with kind `21059`.
* MUST use the private key corresponding to `recipient_pubkey` from the
  selected offer as the sender key for the response rumor and seal.
* MUST set the rumor `content` to exactly one encoded BOLT 12 invoice
  string, beginning with `lni`.
* MUST use the BOLT 12 invoice human-readable prefix `lni`,
  case-insensitively.
* MUST ensure the rumor `content` is at most 32768 bytes when UTF-8
  encoded.
* MUST include exactly one `["bolt12", "invoice"]` tag.
* MUST include exactly one `e` tag, where
  `request_rumor_id` is the lowercase 64-character hexadecimal id of the
  decrypted request rumor event, and MUST set that tag's second element to
  `request_rumor_id`.
* MUST include exactly one `p` tag, and MUST set that tag's second element
  to `payer_pubkey`, the lowercase 64-character hexadecimal pubkey from
  the decrypted request rumor event's `pubkey` field, which the
  sender-binding check has confirmed equals the request seal pubkey.
* MUST seal and gift-wrap the response according to [NIP-59][] addressed
  to `payer_pubkey`.
* MUST include exactly one public `p` tag in the outer `kind:1059` gift
  wrap, and that tag's second element MUST be `payer_pubkey`.
* MUST publish the response to one or more valid relays advertised by the
  payer using `["relay", relay_url]` tags that the offer issuer is allowed
  to connect to, if any remain after validation.
* MUST publish the response to the relay or relays where it received the
  request if no valid payer-advertised relay remains that the offer issuer
  is allowed to connect to.
* MAY also publish the response to the relay or relays where it received
  the request.

The payer receiving a Nostr invoice response:

* MUST, before decrypting the gift-wrap content, validate the outer
  gift-wrap event kind, id, pubkey, and signature as specified above.
* MUST, before decrypting the gift-wrap content, ignore the message if the
  outer `kind:1059` gift wrap does not contain exactly one public `p` tag,
  or if that tag's second element is not the fresh Nostr pubkey it used
  for the request.
* MUST unwrap the [NIP-59][] message.
* MUST ignore the message if the decrypted rumor event kind is not
  `21059`.
* MUST ignore the message if the decrypted rumor event pubkey is not the
  `recipient_pubkey` from the offer, encoded as a lowercase 64-character
  hexadecimal string.
* MUST ignore the message if it does not contain exactly one `p` tag, or
  if that tag's second element does not match the fresh Nostr pubkey it
  used for the request.
* MUST ignore the message if it does not contain exactly one
  `["bolt12", "invoice"]` tag.
* MUST ignore the message if it does not contain exactly one `e` tag, or
  if that tag's second element does not match the request rumor id it
  sent.
* MUST ignore the message if the rumor content exceeds 32768 bytes when
  UTF-8 encoded.
* MUST parse the rumor content as a BOLT 12 `invoice` with human-readable
  prefix `lni`, case-insensitively.
* MUST validate the invoice according to BOLT 12.
* MUST reject the invoice if any field in the ranges copied from the
  `invoice_request` is missing from the invoice or does not exactly match
  the invoice request.
* MUST reject the invoice if `invoice_node_id` is not equal to the
  `offer_issuer_id` from the offer.
* MUST reject the invoice if its signature is not valid for
  `invoice_node_id`.

The BOLT 12 requirements that an invoice response arrive via the
`onionmsg_tlv` `reply_path`, or via an `invreq_paths` blinded path if the
`invoice_request` contains `invreq_paths`, do not apply when the payer
intentionally uses the Nostr transport defined in this bLIP.

### Error Responses

If the offer issuer cannot return an invoice, it SHOULD send a Nostr error
response.

The offer issuer sending an error response:

* MUST create a Nostr rumor event with kind `21059`.
* MUST use the private key corresponding to `recipient_pubkey` from the
  selected offer as the sender key for the error rumor and seal.
* MUST include exactly one `["bolt12", "error"]` tag.
* MUST include exactly one `e` tag, where
  `request_rumor_id` is the lowercase 64-character hexadecimal id of the
  decrypted request rumor event, and MUST set that tag's second element to
  `request_rumor_id`.
* MUST include exactly one `p` tag, and MUST set that tag's second element
  to `payer_pubkey`, the lowercase 64-character hexadecimal pubkey from
  the decrypted request rumor event's `pubkey` field, which the
  sender-binding check has confirmed equals the request seal pubkey.
* MUST set `content` to the UTF-8 JSON serialization of an object with
  the following fields:

```json
{
  "code": "invalid_invoice_request",
  "message": "The invoice request could not be parsed."
}
```

The offer issuer MUST seal and gift-wrap the error response according to
[NIP-59][] addressed to `payer_pubkey`, and MUST include exactly one
public `p` tag in the outer `kind:1059` gift wrap whose second element is
`payer_pubkey`. The offer issuer MUST ensure the error rumor `content` is
at most 32768 bytes when UTF-8 encoded. The offer issuer MUST publish the
error response to one or more valid relays advertised by the payer using
`["relay", relay_url]` tags that the offer issuer is allowed to connect
to, if any remain after validation. The offer issuer MUST publish the error
response to the relay or relays where it received the request if no valid
payer-advertised relay remains that the offer issuer is allowed to connect
to. The offer issuer MAY also publish the error response to the relay or
relays where it received the request.

The following error codes are defined:

| Code                      | Description                                              |
|---------------------------|----------------------------------------------------------|
| `invalid_invoice_request` | The request body is not a valid BOLT 12 invoice request. |
| `unknown_offer`           | The invoice request does not match a known offer.        |
| `offer_expired`           | The matching offer has expired.                          |
| `rejected`                | The invoice request is valid but was rejected.           |
| `rate_limited`            | The offer issuer is rate-limiting this client or request.|
| `temporarily_unavailable` | The offer issuer cannot currently generate an invoice.   |

The payer:

* MUST, before decrypting the gift-wrap content, validate the outer
  gift-wrap event kind, id, pubkey, and signature as specified above.
* MUST, before decrypting the gift-wrap content, ignore the message if the
  outer `kind:1059` gift wrap does not contain exactly one public `p` tag,
  or if that tag's second element is not the fresh Nostr pubkey it used
  for the request.
* MUST unwrap the [NIP-59][] message.
* MUST ignore the message if the decrypted rumor event kind is not
  `21059`.
* MUST ignore the message if the decrypted rumor event pubkey is not the
  `recipient_pubkey` from the offer, encoded as a lowercase 64-character
  hexadecimal string.
* MUST ignore the message if it does not contain exactly one `p` tag, or
  if that tag's second element does not match the fresh Nostr pubkey it
  used for the request.
* MUST ignore the message if it does not contain exactly one
  `["bolt12", "error"]` tag.
* MUST ignore the message if it does not contain exactly one `e` tag, or
  if that tag's second element does not match the request rumor id it
  sent.
* MUST ignore the message if the rumor content exceeds 32768 bytes when
  UTF-8 encoded.
* MUST parse the rumor content as the UTF-8 JSON serialization of an
  object.
* MUST ignore the message if the parsed JSON object contains duplicate
  member names.
* MUST ignore the message if the parsed JSON object does not contain a
  string `code` field whose value is one of the error codes defined in
  this section.
* MUST ignore the message if the parsed JSON object does not contain a
  string `message` field.
* MUST treat a valid error response as failure to obtain an invoice.
* SHOULD NOT directly display the `message` field to users unless it has
  filtered problematic characters.
* MAY retry transient errors according to local policy.

### Timeouts and Retries

Nostr relays do not guarantee delivery. A payer SHOULD use a local timeout
for invoice responses.

A payer MAY publish the same request gift wrap to multiple relays from the
offer. A payer SHOULD NOT create multiple distinct invoice requests for a
single user authorization unless the previous request has timed out or the
user has authorized a retry.
A payer SHOULD use exponential backoff when retrying after a timeout or
transient error.

The offer issuer MAY return the same invoice for a repeated invoice request
with the same `invreq_metadata`, as allowed by BOLT 12.
Offer issuers SHOULD deduplicate concurrent requests with identical
`invreq_metadata` and return the same invoice for each.

## Rationale

[NIP-59][] gift wraps and [NIP-44][] encryption are used instead of
[NIP-04][] encrypted direct messages because NIP-04 is deprecated and
leaks more metadata.
The offer TLV type is an arbitrary unused odd type in the BOLT 12
offer-extension range. It is odd because this transport is optional and
readers that do not understand it can ignore it; it is not intended to
encode the bLIP number and should not change solely because this bLIP is
renumbered.

This bLIP uses a custom rumor kind instead of [NIP-17][] `kind 14`
because the message is not a human chat message. It nevertheless follows
NIP-17's sender-binding rule so the decrypted rumor pubkey is bound to
the signed seal pubkey.

The rumor kind is never visible to relays because the rumor is sealed and
gift-wrapped in a `kind:1059` event. The choice of `21059` in the
ephemeral range is an arbitrary bLIP-defined identifier and has no relay
routing semantics; it is not intended to encode the bLIP number and should
not change solely because this bLIP is renumbered.

The offer carries explicit relays instead of relying on Nostr profile relay
discovery so that the BOLT 12 offer is self-contained. Implementations may
still use normal Nostr discovery mechanisms as a supplement, but they are not
required for this bLIP.
Relay URLs are encoded as byte vectors so that `url_len` unambiguously
counts bytes in the UTF-8 encoding; readers still validate that each value
is valid UTF-8 and a valid relay URL.

The payer uses a fresh Nostr key pair for each request to reduce correlation
between invoice requests. The BOLT 12 `invreq_payer_id` remains the key used
for BOLT 12 payer semantics; the Nostr key is only a transport key.

The response includes the request rumor id in an encrypted `e` tag so the
payer can match responses to requests without exposing that correlation to
relays.
The 32768-byte rumor content cap is below the [NIP-44][] plaintext limit
and bounds BOLT 12 parsing work. The larger 131072-byte outer gift-wrap
cap allows NIP-44 ciphertext and Nostr event overhead while bounding
pre-validation parsing, hashing, and signature work.
If an offer advertises both this transport and another alternate transport
with a larger body limit, the issuer SHOULD ensure returned invoice
encodings fit within this transport's 32768-byte rumor content cap if it
expects payers to use Nostr.

Related work includes [BIP-353][], [NIP-57][] Nostr zaps, signed offers in
[bLIP 56][], and the manual exchange in [bLIP 58][]. BIP 353 discovers
BOLT 12 offers via DNS payment instructions, but does not transport the
interactive invoice request flow. An offer carrying this TLV MAY be
distributed via BIP 353, which composes DNS offer discovery with Nostr
invoice-request transport. bLIP 56 signs the offer so that the Nostr
recipient key and relay set are bound to `offer_issuer_id` before the
payer sends an `invoice_request`. Zaps use Nostr events for Lightning
payment requests and receipts, but they are not a BOLT 12
`invoice_request` and `invoice` transport and commonly carry BOLT 11
invoices. This bLIP uses encrypted [NIP-59][] messages to transport native
BOLT 12 objects while preserving BOLT 12 invoice validation semantics.
[bLIP 58][] defines a local, user-mediated alternative for QR, copy-paste,
NFC, or file handoff; this bLIP instead defines an automated relay-based
transport advertised in the offer.

The offer is required to include `offer_issuer_id` because Nostr does not
provide the onion-message path context used by BOLT 12 offers containing only
`offer_paths`. The payer can instead verify that the returned invoice is
signed by the advertised `offer_issuer_id`.

When this transport is intentionally used, BOLT 12 onion-message arrival
checks for `offer_paths`, `reply_path`, and `invreq_paths` are replaced by
Nostr delivery and BOLT 12 invoice signature validation. All BOLT 12 object
validation that does not depend on onion-message delivery still applies.

## Privacy and Security Considerations

Nostr transport has different privacy properties than onion messages.

Relays and network observers can learn:

* The IP address or proxy address used by the payer and offer issuer.
* The relays used by both parties.
* The reusable recipient Nostr public key from the offer.
* Timing and approximate size of request and response messages.
* That a payer contacted a relay used by a particular offer issuer.

[NIP-59][] hides the invoice request and invoice contents from relays,
but it does not provide forward secrecy or guaranteed delivery. Relays may
store messages, censor messages, fail to deliver messages, or correlate
metadata across connections.

[NIP-59][] gift wraps use one-time signing keys and randomized timestamps
to reduce metadata correlation. Implementations MUST follow those
requirements for this transport.

Relays cannot see the encrypted rumor kind `21059`, but they can observe
gift-wrapped events addressed to the offer's advertised Nostr public key.
Relay operators should assume such events may carry payment-flow metadata.
If the offer was discovered via BIP 353, DNS discovery metadata is
additional to the Nostr relay and network metadata described here and is
visible to different observers.

The signed-offer requirement in this bLIP prevents recipient-substitution
relay attacks before the payer sends an `invoice_request`: a party that
changes only the Nostr recipient key or relays in an otherwise real signed
offer cannot produce a valid `offer_signature`. The selected-offer checks
at the issuer provide an additional check that the invoice request matches
the offer selected by the Nostr recipient key. This does not authenticate
the offer identity by itself. If an attacker substitutes an entirely
different signed offer, the returned invoice can still validate under the
attacker's `offer_issuer_id`; preventing that requires authenticated offer
delivery or an independently known issuer key.

Payers MUST use a fresh Nostr key pair for each invoice request. Reusing the
same Nostr key across requests can link those requests.

Payers SHOULD use fresh `invreq_metadata` and a fresh `invreq_payer_id` for
each invoice request, as required by BOLT 12, and MUST NOT reuse payer keys
across requests in a way that creates additional correlation.

Payers SHOULD prefer standard BOLT 12 onion-message transport when it is
available and reliable. Wallets SHOULD make the privacy tradeoff clear to
users when Nostr transport is used interactively.

The offer issuer should expect unsolicited messages to its advertised Nostr
key. Offer issuers SHOULD rate-limit invoice request handling and MAY use
relay-level mitigations such as [NIP-42][] authenticated relays or
[NIP-13][] proof-of-work where appropriate.

Nostr signatures and encryption authenticate and protect the transport
messages, but they do not replace BOLT 12 invoice validation. Payers MUST
validate the returned invoice and its BOLT 12 signature before paying.

## Universality

This feature is optional and is not intended to be universal. BOLT 12 onion
messages remain the standard transport for interactive BOLT 12 invoice
requests.

This bLIP is intended for deployments that want a relay-based asynchronous
fallback or out-of-band transport while preserving BOLT 12 object semantics.

## Backwards Compatibility

Older BOLT 12 readers that do not understand
`offer_invoice_request_nostr_endpoint` can ignore it and use standard BOLT
12 onion-message transport if the offer contains usable routing information.

Offers that rely exclusively on this bLIP will not be payable by wallets
that do not implement this bLIP.
