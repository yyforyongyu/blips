## Abstract

This bLIP defines an optional manual exchange profile for BOLT 12 offer
payments.

A payer that supports this bLIP can obtain a BOLT 12 offer, construct an
encoded BOLT 12 `invoice_request`, present that request to the offer
issuer over a manual channel, and receive an encoded BOLT 12 `invoice`
over a manual channel.

Manual channels include QR codes, copy-paste, NFC handoff, local file
transfer, or any other user-mediated channel that preserves the encoded
BOLT 12 strings.

This bLIP only specifies an alternate transport for the interactive BOLT
12 invoice request flow. It does not change BOLT 12 offer, invoice
request, invoice, or payment semantics, and it does not define any new
TLV fields.

## Motivation

BOLT 12 offers are often displayed as QR codes in local or in-person
contexts. A payer may be able to scan an offer but may not be able to
send the resulting `invoice_request` over onion messages, HTTPS, Nostr,
or another automated network transport.

This bLIP standardizes the simplest fallback: exchange the native BOLT
12 encoded objects directly through a user-mediated channel. This enables
local, in-person, or restricted-network invoice-request workflows while
preserving BOLT 12 object validation.

This profile is useful when preserving BOLT 12 semantics is the goal, such
as reusing the same offer, invoice request, and invoice validation flow
across transports. It is not intended to be a better attended point-of-sale
flow than displaying a single BOLT 11 invoice.

## Specification

### Manual Channel

A manual channel is a bidirectional, user-mediated exchange that carries
encoded BOLT 12 strings without using an endpoint advertised in the
offer.

Examples include:

* A payer copies an encoded invoice request string into a local point of
  sale terminal and copies the returned encoded invoice string back into
  the wallet.
* Two applications transfer the encoded strings using same-device app
  handoff, an operating-system share sheet, NFC, local wireless handoff,
  USB, local file transfer, or another local mechanism.
* A payer scans an offer QR code, displays an invoice request QR code,
  then scans an invoice QR code from the offer issuer.

The manual channel MAY be unauthenticated and unencrypted. Implementations
MUST NOT treat properties of the manual channel as a substitute for BOLT
12 validation.

### Offer Requirements

The writer of an offer:

* MAY support this bLIP without adding any TLV field to the offer.
* If it expects payers to use this bLIP:
  * MUST include `offer_issuer_id`.
  * SHOULD keep the offer available for manual exchange until the offer
    expires.
  * MAY also include `offer_paths` or other alternate transports.

The reader of an offer:

* MAY ignore support for this bLIP.
* MUST NOT use this bLIP unless the local user interface or out-of-band
  context indicates that the offer issuer can receive an encoded
  `invoice_request` and return an encoded `invoice` over a manual
  channel.
* MUST NOT use this bLIP if the offer does not contain `offer_issuer_id`.

If an offer contains `offer_paths`, the payer MAY use either the standard
onion-message transport or the manual exchange defined in this bLIP.

When using this bLIP, the payer MUST use `offer_issuer_id` as the
expected BOLT 12 `invoice_node_id` for the returned invoice, even if the
offer also contains `offer_paths`.

### Encoded Objects

Each manual-channel payload:

* MUST contain exactly one encoded BOLT 12 string.
* MUST use the expected BOLT 12 human-readable prefix for its role:
  * `lno` for an offer.
  * `lnr` for an invoice request.
  * `lni` for an invoice.
* MUST be parsed according to the BOLT 12 encoding rules.
* MUST NOT exceed 65536 bytes when encoded as ASCII.
* MUST NOT contain leading or trailing whitespace.

Writers of QR code payloads:

* SHOULD use uppercase BOLT 12 encoding, as recommended by BOLT 12 for QR
  codes.
* SHOULD NOT include `+` continuation markers or embedded whitespace.
* MUST encode the complete payload in a single QR code symbol when using
  the QR profile in this bLIP.

Readers of QR code payloads:

* MUST handle uppercase and lowercase BOLT 12 encodings.
* MUST handle `+` continuation markers and whitespace as required by BOLT
  12.
* MUST fail the QR profile if the complete payload is not recovered as a
  single encoded BOLT 12 string.

This bLIP does not define animated QR codes, multipart QR codes, or any
fragmentation framing. Implementations MAY use such mechanisms by local
agreement, but they are outside this bLIP and MUST reassemble to exactly
one encoded BOLT 12 string before applying this specification.

### Payment Flow

The manual offer payment flow is:

1. The payer obtains an encoded BOLT 12 offer.
2. The payer validates the offer according to BOLT 12.
3. The payer constructs a BOLT 12 `invoice_request` exactly as specified
   by BOLT 12.
4. The payer transfers the encoded `invoice_request`, beginning with
   `lnr`, to the offer issuer over a manual channel.
5. The offer issuer validates the `invoice_request` and generates a BOLT
   12 `invoice`.
6. The offer issuer transfers the encoded `invoice`, beginning with
   `lni`, to the payer over a manual channel.
7. The payer validates the invoice according to BOLT 12 and pays it only
   if it matches the payer's authorization.

### Invoice Request

The payer constructs a BOLT 12 `invoice_request` exactly as specified by
BOLT 12.

The payer:

* MUST preserve the invoice request and the secret key corresponding to
  `invreq_payer_id` until it has either accepted an invoice or abandoned
  the attempt.
* MUST transfer exactly one encoded BOLT 12 invoice request string,
  beginning with `lnr`, to the offer issuer.
* SHOULD label the displayed or transferred request as intended for the
  offer issuer, not as an invoice to be paid.

The offer issuer receiving an invoice request over this bLIP:

* MUST parse the payload as exactly one encoded BOLT 12 `invoice_request`.
* MUST validate the invoice request according to BOLT 12, except that the
  request is allowed to arrive over the manual exchange defined in this
  bLIP instead of over onion messages.
* MUST NOT reject or ignore the invoice request solely because the
  matching offer contains `offer_paths` and the invoice request did not
  arrive via one of those blinded paths.
* MUST NOT reject or ignore the invoice request solely because it contains
  `invreq_paths` that cannot be used for the manual response.
* MUST verify that the invoice request matches a valid, unexpired offer
  for which the offer issuer is willing to use this bLIP.
* MUST reject the invoice request if the matching offer does not contain
  `offer_issuer_id`.
* MUST set `invoice_node_id` in the returned invoice to `offer_issuer_id`.
* MUST sign the invoice according to BOLT 12.
* MAY return the same invoice for a repeated invoice request with the same
  `invreq_metadata`, as allowed by BOLT 12.
* SHOULD deduplicate repeated or concurrent requests with identical
  `invreq_metadata` and return the same invoice for each.

### Invoice Response

The offer issuer returning an invoice over this bLIP:

* MUST transfer exactly one encoded BOLT 12 invoice string, beginning with
  `lni`, to the payer.
* MUST ensure the encoded invoice does not exceed 65536 bytes.
* SHOULD label the displayed or transferred invoice as intended for the
  payer that presented the invoice request.

The payer receiving an invoice over this bLIP:

* MUST parse the payload as exactly one encoded BOLT 12 `invoice`.
* MUST validate the invoice according to BOLT 12.
* MUST reject the invoice if any field in the ranges copied from the
  `invoice_request` is missing from the invoice or does not exactly match
  the invoice request.
* MUST reject the invoice if `invoice_node_id` is not equal to the
  `offer_issuer_id` from the offer.
* MUST reject the invoice if its signature is not valid for
  `invoice_node_id`.
* MUST reject the invoice if the amount, description, quantity, chain, or
  any other user-authorized payment parameter is not acceptable to the
  payer.
* MUST NOT treat the identity of the display, camera, clipboard, device,
  user, or local channel as a substitute for BOLT 12 invoice validation.

The BOLT 12 requirements that an invoice response arrive via the
`onionmsg_tlv` `reply_path`, or via an `invreq_paths` blinded path if the
`invoice_request` contains `invreq_paths`, do not apply when the payer
intentionally uses the manual exchange defined in this bLIP.

### Errors and Retries

This bLIP does not define a machine-readable error response.

If the offer issuer cannot return an invoice, it SHOULD indicate failure
through the local user interface or through the same out-of-band context
used for the manual exchange.

A payer SHOULD NOT create multiple distinct invoice requests for a single
user authorization unless the previous request has been abandoned, has
timed out according to local policy, or the user has authorized a retry.

## Rationale

This bLIP does not define an offer TLV because a manual channel is not an
endpoint. Whether manual exchange is possible depends on the user
interface and local context, such as whether a point-of-sale terminal can
scan an `lnr...` string and display an `lni...` string. Adding a TLV would
increase offer size without providing a routable destination.

The exchange uses the existing BOLT 12 encoded strings directly. This
keeps the transport profile thin and avoids creating another object
encoding.

The offer is required to include `offer_issuer_id` because the manual
channel does not provide the onion-message path context used by BOLT 12
offers containing only `offer_paths`. The payer can instead verify that
the returned invoice is signed by the advertised `offer_issuer_id`.

When this transport is intentionally used, BOLT 12 onion-message arrival
checks for `offer_paths`, `reply_path`, and `invreq_paths` are replaced by
manual delivery and BOLT 12 invoice signature validation. All BOLT 12
object validation that does not depend on onion-message delivery still
applies.

QR codes are included as a profile because they are common for local BOLT
12 offer presentation. Uppercase BOLT 12 strings fit QR alphanumeric mode
more efficiently than lowercase strings. In this manual profile, offers and
invoice requests usually do not need `offer_paths` or `invreq_paths` for
delivery to the issuer, which helps keep those QR payloads small. The
invoice leg may still exceed practical single-QR capacity if it contains
large blinded payment paths. Multipart QR framing is not defined because it
would require an additional fragmentation, ordering, and integrity layer;
implementations that need large payloads should use another transport or a
separately specified fragmentation scheme.

Related work includes signed offers in [bLIP 56][], the HTTPS transport in
[bLIP 57][], and the Nostr transport in [bLIP 59][]. bLIPs 57 and 59
define automated network transports advertised inside an offer. This
bLIP instead defines a local, user-mediated exchange that does not require
an advertised endpoint. bLIP 56 can provide offer integrity for manual
channels when the payer expects a signed offer or knows the issuer key.

## Privacy and Security Considerations

Manual exchange does not create DNS, TLS, relay, or payer-IP metadata for
the invoice request transport itself. This does not mean it has no privacy
leaks.

Anyone who can observe, record, photograph, scan, log, back up, or
otherwise access the manual channel may learn information from the
encoded objects, including:

* The offer being paid.
* The timing and approximate size of the exchange.
* The full `invoice_request`, which may include amount, quantity, payer
  note, and payer public key fields.
* The full `invoice`, including the invoice amount, payment hash, invoice
  paths, and other invoice fields.

The offer issuer also observes the full `invoice_request`. This is
expected because the offer issuer must construct the invoice, but manual
exchange can expose the same data to nearby observers, cameras,
screen-capture tools, clipboard managers, accessibility services, logs,
or application analytics.

Captured manual-channel payloads can be replayed. Offer issuers SHOULD
deduplicate repeated invoice requests with the same `invreq_metadata` and
return the same invoice where possible. Payers MUST validate that any
invoice they receive matches the invoice request they created before
paying.

A person, device, or application that relays unchanged manual-channel
payloads between the payer and offer issuer can observe or censor the
exchange. BOLT 12 invoice validation prevents such a relay from modifying
the invoice or redirecting payment without detection, but it does not make
the manual channel private.

Manual exchange does not authenticate the physical counterparty. An
attacker can display a malicious offer, substitute an invoice QR code, or
trick a user into scanning the wrong object. Wallets SHOULD clearly label
offer, invoice request, and invoice screens, and SHOULD ask the payer to
confirm the payment details before paying.
Signed offers as defined in [bLIP 56][] can help detect tampering with a
known issuer's offer, but they do not prevent substitution with a different
signed offer unless the payer knows which issuer key to expect.

Payers SHOULD use fresh `invreq_metadata` and a fresh `invreq_payer_id` for
each invoice request, as required by BOLT 12, and MUST NOT reuse payer keys
across requests in a way that creates additional correlation.

Applications SHOULD avoid unnecessary persistence, logging, analytics, or
cloud backup of encoded manual-channel payloads. Applications using the
system clipboard SHOULD avoid leaving BOLT 12 payloads there longer than
necessary when the platform allows this.

Payers SHOULD prefer standard BOLT 12 onion-message transport when it is
available and reliable. Wallets SHOULD make the privacy tradeoff clear to
users when manual exchange is used interactively.

## Universality

This feature is optional and is not intended to be universal. BOLT 12
onion messages remain the standard transport for interactive BOLT 12
invoice requests.

This bLIP is intended for local, in-person, or restricted-network
invoice-request workflows where a user-mediated exchange is practical and
preserving BOLT 12 object semantics is desired.

## Backwards Compatibility

This bLIP defines no new TLV fields and does not change BOLT 12 object
encoding.

Older BOLT 12 implementations that do not support this bLIP are unaffected
and can continue using standard BOLT 12 onion-message transport or any
other supported transport.

Offers that rely on manual exchange will not be payable through this flow
by wallets or point-of-sale systems that cannot display, scan, copy, or
otherwise transfer encoded `lnr...` and `lni...` strings.
